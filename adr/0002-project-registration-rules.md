# ADR-0002: 프로젝트 등록·사례 재구성 규칙

- 상태: **결정**
- 날짜: 2026-10-22
- 담당: BE (기획 결정)
- 관련: 기획서 2장·F1·F2·F3·4.3·4.4·5.4·5.5·S05·S06·8장·9장, 작업목록 D-2·D-3·D-5, FE-08·FE-10, BE-08~10·BE-12, AI-05

## 배경

BE 도메인 모델링(`BE-nerdnam/docs/02-도메인-모델.md`) 중 기획서에 없거나 모호한 규칙 10개(Q1~Q10)와 작업목록의 D-2·D-3·D-5를 정리해 결정했다.

## 결정

| ID | 질문 | 결정 |
| --- | --- | --- |
| Q1 | 생성 횟수 상한 n | **없앤다.** 나누기·다시 나누기·사례 수정 요청을 횟수 제한 없이 할 수 있다. 생성 횟수(`generation_count`)는 통계·비용 측정용으로만 기록한다. |
| Q2 | 확인 질문 답변으로 새 버전 만들기 | 횟수 제한 없이 할 수 있다 (Q1에 따름). |
| Q3 | AI 호출이 실패하면 횟수는? | 상한이 없으므로 문제가 되지 않는다. 기록은 성공해서 반영한 경우만 센다. |
| Q4 | 확정한 프로젝트를 다시 고치면? | 다시 확정하기 전까지 기존 확정 사례의 청크는 검색에 계속 쓴다. 고치는 방법은 Q6의 재등록을 따른다. |
| Q5 | 나눈 뒤 원문(본문)을 고치면? | ~~고칠 수 있지만 사례 위치(`source_spans`)가 틀어지므로 "다시 나누기 필요"로 표시하고, 다시 나누기 전에는 프로젝트를 확정할 수 없다.~~ → **기획서 v1.14에서 바뀜** (아래 "변경") |
| Q6 | 확정·제외한 사례를 검토 중으로 되돌릴 수 있나? | 프로젝트 확정 전에는 가능(결정 취소). **확정 후에 프로젝트 내용을 고치려면 등록 과정 전체(입력 → 나누기 → 사례별 결정 → 확정)를 다시 거친다. 기존 내용은 맥락으로 남는다.** (아래 "재등록") |
| Q7 | 경력·프로젝트에 쓰인 기술을 기술스택에서 지우면? | 막고 "OO 경력에서 사용 중"처럼 어디서 쓰는지 안내한다. |
| Q8 | 프로젝트가 연결된 경력을 지우면? | 막거나, 프로젝트 소속을 개인으로 바꾸도록 안내한다. |
| Q9 | 연차 계산 시 겹치는 재직기간은? | 합집합으로 계산한다 (겹치는 기간은 한 번만). |
| Q10 | 확인 질문의 "빼고 진행"은? | 그 질문의 내용을 뺀 새 버전을 만든다. AI를 호출하지 않는다. |
| D-2 | 다시 나누기 때 확정한 사례 유지 여부 | 현재 기획대로 **모든 사례의 결정을 초기화**한다. 이전 사례는 지우지 않고 "대체됨(`superseded`)"으로 기록만 남긴다. |
| D-3 | 연차 계산에 개인·팀 프로젝트 기간 포함 여부 | 포함하지 않는다 (경력 재직기간만). |
| D-5 | 연차 규칙 판정과 LLM 판정이 다를 때 | **낮은 쪽**을 최종 판정으로 한다 (미충족 < 부분 충족 < 충족). |

## 재등록 (확정 후 수정)

1. S06에서 확정한 프로젝트의 "편집"을 누르면 재등록을 시작한다. 프로젝트는 `초안`으로 돌아가고, 기존 원문·사용 기술·링크·확인 질문 답변이 채워진 S04 화면부터 시작한다.
2. 이전 사례와 버전은 지우지 않는다. 다시 나누기를 하면 이전 사례는 `superseded`가 되고, AI에는 이전 확정 사례를 참고 입력(맥락)으로 보낸다 (`/restructure`의 "기존 에피소드 목록").
3. 다시 확정하기 전까지 이전 확정 사례의 청크는 검색에 계속 쓰인다. S06에는 "재등록 중"으로 표시한다.
4. 다시 확정하면 그 프로젝트의 청크(episode, project_summary)를 새로 확정한 사례 기준으로 통째로 바꾼다.

## 영향

| 담당 | 바뀌는 것 |
| --- | --- |
| FE | S05에서 "남은 횟수" 표시 제거, 결정 취소 추가, "다시 나누기 필요" 표시. S06 "편집"이 재등록 흐름으로 들어가고 "재등록 중" 상태 표시 (FE-08, FE-10) |
| BE | 생성 횟수 상한 검사 제거(기록은 유지), 나누기 회차 기록, 재등록 상태 전이, 다시 나누기 필요 플래그, 재확정 시 프로젝트 청크 일괄 교체, 기술·경력 삭제 전 사용 여부 검사, 연차 합집합 계산, 판정 결합 "낮은 쪽" (BE-08~10, BE-12) |
| AI | `/restructure`가 재등록 때 이전 확정 사례를 맥락으로 받는다 (AI-05) |

## 위험과 대응

- **상한이 없어지면 LLM 호출이 늘 수 있다** (기획서 8장 "LLM 서빙 비용"의 대응 중 하나였던 "재구성 반복 상한 n"이 빠짐). 대응: 같은 프로젝트의 AI 생성 요청은 동시에 1건만 처리하고, 회원별·일별 호출량을 BE의 AI 호출 기록으로 모니터링한다. 비정상 사용이 보이면 상품 규칙이 아닌 남용 방지용 속도 제한을 추가한다.
- KPI "재구성 동의율(2회 이내 생성으로 확정)"과 "평균 재구성 횟수"는 사례 버전 기록으로 그대로 측정한다.

## 추후 개발 예정 (MVP 이후)

D-2를 "초기화"로 정했지만, 다음 두 기능을 추후 개발 후보로 남긴다. BE는 나누기 회차(`split_round`)와 대체된 사례 기록을 MVP부터 저장해 두어 나중에 데이터 이전 없이 붙일 수 있게 한다.

1. **부분 다시 나누기:** 사례 3개 중 2개는 마음에 들고 1개만 마음에 들지 않을 때, 마음에 들지 않는 사례만 다시 만들고 나머지의 결정은 유지한다. (AI `/restructure`에 대상 사례 범위를 지정하는 모드 필요)
2. **회차 비교:** 기존 사례를 기록으로 남긴 채 새 사례들을 만들어, 이전 회차와 새 회차를 나란히 보고 고를 수 있게 한다.

## 변경

- **2026-10-22, 기획서 v1.14 · Q5:** "다시 나누기 필요" 표시 대신 **검토 결과 유지 규칙**을 쓴다. 확정 전 검토 결과는 S04(원문 화면)에 들어가거나 S05에서 온보딩 밖으로 나가면 버리므로(경고 후), 원문과 사례가 어긋난 상태가 생기지 않는다. 원문을 고친 뒤에는 S04의 "재구성하기"로 새로 나눈다. 자세한 규칙은 기획서 F2. "다시 나누기 필요" 플래그는 필요 없어진다(BE-09).

## 남은 질문

- 재등록을 도중에 그만두고 이전 확정본으로 돌아가는 "재등록 취소"를 MVP에 넣을지. (넣지 않으면 그만둔 프로젝트는 `초안`으로 남고, 이전 청크는 계속 검색된다.)
