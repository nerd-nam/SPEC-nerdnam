# ADR-0006: 요건 판정 기준 (충족·부분 충족·미충족)과 사람 검수 기준

- 상태: **제안**
- 날짜: 2026-10-26
- 담당: AI (BE와 함께)
- 관련: 기획서 F5·5.4·5.6·7.1·9.1(매칭 정확도), 작업목록 AI-07·AI-11·AI-12·AI-13·BE-12, ADR-0002(D-3·D-5), ADR-0003, `fixtures/match.json`

## 배경

- **KPI 매칭 정확도:** "요건별 판정이 사람 검수와 일치하는 비율 85% 이상"(기획서 9.1). 그런데 사람이 무엇을 기준으로 검수하는지 정해져 있지 않다.
- **P3 프롬프트(`p3_v2`)에 정의가 있지만 경계가 비어 있다.** 다음 같은 경우는 사람마다 판정이 갈린다.
  - 인접 기술: MySQL 경험으로 "PostgreSQL" 요건을 판정할 때
  - 규모 차이: "대용량"에 수치가 없을 때
  - "Kafka **등** 메시지 큐"처럼 예시를 든 요건
  - 기술 목록만 있고 사례가 없을 때
- **AI-11 평가 세트**는 이 기준으로 정답을 만든다. 기준이 없으면 정답이 검수자마다 달라져 85%를 잴 수 없다.

## 결정

### 1. 판정 범위

- **판정 단위는 요건 한 줄이다.** 근거는 그 요건의 후보 청크(검색 상위 최대 20개, `/match` 입력) 안에서만 찾는다. 후보에 없는 사실은 없는 것으로 본다.
- **연차는 AI가 판정하지 않는다.**
  - API가 경력 재직기간으로 규칙 판정을 한다. 겹치는 기간은 한 번만 세고, 개인·팀 프로젝트는 넣지 않는다 (ADR-0002 D-3).
  - 최종 판정은 규칙 판정과 AI 판정 중 **낮은 쪽**이다 (D-5).
  - "Java 3년 이상"이면 AI는 Java 경험만 판정한다.
- **필수·우대 구분은 판정에 영향이 없다.** 같은 기준으로 판정한다. 구분은 충족률 계산과 갭 가이드 문구에만 쓴다.
- **확실하지 않으면 한 단계 낮게 판정한다.** `met`을 `partial`로, `partial`을 `unmet`으로 내린다 (P3 사실 규칙).
  - 높게 틀리면 사용자가 없는 경험을 내세우게 된다. 낮게 틀리면 갭 가이드가 보완할 길을 알려 준다. 그래서 높게 틀리는 쪽이 더 나쁘다.

### 2. 판정 정의

| 판정 | 정의 | 근거 |
| --- | --- | --- |
| `met` 충족 | 후보 중에 요건의 기술·업무·역할을 **직접** 해낸 내용이 있다 | 1개 이상. 구체적인 경험(`episode`·`career`·`project_summary`)을 기술 목록(`skill`)보다 먼저 쓴다 |
| `partial` 부분 충족 | 관련 경험이 있지만 요건의 **일부만** 보여 준다 (아래 경계 표) | 1개 이상. 무엇이 부족한지 `reason`에 쓴다 |
| `unmet` 미충족 | 요건과 관련된 경험이 후보에 없다 | 빈 목록. 근거 없는 `met`·`partial`은 `unmet`이 된다 (AI 서버·BE 공통 규칙) |

### 3. 경계 기준

경계 사례를 판정하는 기준이다. 검수자는 판정이 갈리면 이 표의 번호로 이야기한다.

| # | 경우 | 판정 | 예 |
| --- | --- | --- | --- |
| B1 | 요건이 **범주를 말하고 예시를 든다** ("A 등 B", "B (A 등)") | 범주 안의 기술이면 `met`. 예시 A가 아니어도 된다 | "Kafka 등 메시지 큐" ← RabbitMQ 운영 = `met` |
| B2 | 요건이 **특정 기술을 말하는데** 경험은 같은 범주의 다른 기술이다 | `partial` | "PostgreSQL 경험" ← MySQL만 = `partial` |
| B3 | 경험이 요건 기술의 **기반·구성 요소만** 있다 | `partial` | "Spring 개발" ← Java만, "Kubernetes 운영" ← Docker만 = `partial` |
| B4 | **"또는"으로 묶인 요건** ("A 또는 B", "A/B 중 하나") | 하나만 있어도 `met` | "Java 또는 Kotlin" ← Kotlin = `met` |
| B5 | **함께 나열한 요건** ("A 및 B", "A, B", "A/B") | 모두 보이면 `met`, 일부만 보이면 `partial` | "RDBMS 설계 및 쿼리 튜닝" ← 인덱스 재설계·실행 계획 분석 = `met` (인덱스 설계는 RDBMS 설계에 든다). 쿼리 튜닝만 있으면 `partial` |
| B6 | **규모를 말하는 요건** ("대용량", "대규모", "MAU 100만") | 규모를 보여 주는 수치나 표현(피크 처리량, 부하 테스트, 트래픽 대응)이 있으면 `met`. 같은 업무지만 규모 근거가 없거나 요건의 수치보다 작으면 `partial` | "대용량 트래픽 처리" ← "프로모션 피크 처리량 약 2배를 장애 없이" = `met`. 같은 API 개발이지만 규모 언급이 없으면 `partial` |
| B7 | 경험이 요건의 **일부 도메인만** 해당 | `partial` | "결제·금융 도메인" ← 커머스 결제만 = `partial` |
| B8 | 요건이 **역할**(설계·구축·리드·주도)을 요구한다 | 그 역할이 적혀 있어야 `met`. 같은 기술을 썼지만 역할이 보이지 않으면 `partial` | "MSA 전환 설계 주도" ← MSA 환경에서 개발만 = `partial` |
| B9 | 요건이 "**운영 경험**·**실무 경험**"이다 | 실서비스에서 썼다는 내용이 있으면 `met`. 인프라 운영 담당일 필요는 없다 | "Kafka 운영 경험" ← 결제 서비스 승인 후처리를 Kafka 비동기로 분리 = `met` |
| B10 | 근거가 **기술 목록(`skill`) 청크뿐**이다 | 숙련도가 `능숙`·`실무 사용`이고 사용처가 있으면 `met`. 단, B6·B8처럼 규모·역할을 요구하면 `partial`. 숙련도가 `학습 중`이면 많아야 `partial` | "Redis 사용 경험" ← `Redis · 실무 사용 · 사용처: 결제 승인 API` = `met`. "Spring Batch 개발" ← `Spring Batch · 학습 중` = `partial` |
| B11 | 근거가 **개인·팀 프로젝트**다 | 기술을 써 본 것이면 `met`. 실서비스 운영·규모를 요구하면 그 내용이 적혀 있을 때만 `met`, 아니면 `partial` | "React 개발" ← 개인 프로젝트에서 React로 구현 = `met` |
| B12 | **태도·역량 요건** ("커뮤니케이션", "협업", "주도적", "문제 해결") | 구체적인 행동(누구와, 무엇을, 어떻게)이 적혀 있으면 `met`. 일반적인 주장이나 역할 이름만 있으면 `partial`. 관련 내용이 없으면 `unmet` | "협업 능력" ← "기획·QA와 일정 조율해 결제 취소 정책 변경" = `met` |
| B13 | **서비스가 받지 않는 정보** (학위·전공·자격증·병역·어학 점수) | `unmet`. `reason`에 "저장된 경험으로는 확인할 수 없음"이라고 쓴다 | "컴퓨터공학 전공" = `unmet` |
| B14 | 후보에 **비슷한 말만** 있다 | 같다고 넘겨짚지 않는다. B1~B7 중 맞는 것이 없으면 `unmet` | "Kafka 운영" ← "문자 메시지 발송 기능 개발"만 있음 = `unmet` |

`fixtures/match.json`의 6개 판정은 위 기준과 맞는다.
- 11번(Java/Spring): `met`, B10·B5
- 12번(RDBMS 설계·튜닝): `met`, B5
- 13번(대용량 트래픽): `met`, B6
- 14번(Kafka 등 메시지 큐 운영): `met`, B1·B9
- 15번(결제·금융): `partial`, B7
- 16번(Kubernetes): `unmet`. 후보에 관련 경험이 없다.

### 4. 사람 검수 기준

AI-11 평가 세트의 정답을 만들 때, 그리고 운영 중 매칭 정확도를 샘플로 검수할 때 쓴다.

**검수 입력**
- 검수자는 AI와 **같은 입력**을 본다. 요건 문구와 그 요건의 후보 청크(최대 20개)다. 후보 밖에서 알게 된 사실은 쓰지 않는다.
- 사용자의 전체 경험에는 근거가 있는데 후보에 없으면 **"검색 누락"** 으로 따로 적는다. 이 경우는 판정 정확도가 아니라 검색 재현율(AI-11, D-12)에서 센다.

**검수 절차**
1. 검수자 2명이 따로 판정한다. 판정, 근거로 볼 수 있는 청크 id 전부, 적용한 경계 번호(B1~B14)를 적는다.
2. 판정이 다르면 경계 번호로 이야기해 하나로 정한다.
3. 합의가 안 되면 **낮은 쪽**을 정답으로 하고 "경계 사례"로 표시한다. 같은 유형이 반복되면 위 경계 표에 행을 추가한다. 이 문서를 고치는 PR로 한다.
4. 표에 없는 유형이 나오면 3번과 같이 행을 추가한다.

**지표**

| 지표 | 계산 | 목표 |
| --- | --- | --- |
| 판정 일치율 | AI 판정이 정답과 같은 요건 수 / 전체 요건 수 (3단계가 정확히 같아야 일치) | **85% 이상** (KPI 매칭 정확도) |
| 과대 판정률 | AI 판정이 정답보다 높은 비율 (`unmet`→`partial`·`met`, `partial`→`met`) | 따로 보고한다. 일치율이 같다면 과대 판정이 적은 쪽을 고른다 |
| 큰 오류 | `met`과 `unmet`이 서로 바뀐 경우 | 건마다 원인을 적는다 |
| 근거 정밀도 | AI 근거 청크 중 정답 근거 목록에 있는 비율 (`met`·`partial`만) | 참고 지표 |
| 이유 사실 오류 | `reason`에 후보에 없는 경험·수치가 있는 요건 수 | 0건 (P3 사실 규칙) |

- **AI 평가(AI-11):** AI 판정(BE의 `llm_verdict`)을 정답과 비교한다. 정답은 연차를 빼고 만든다.
- **운영 검수(KPI):** 최종 판정(규칙 판정과 결합한 `final_verdict`)을 검수한다. 이때 연차는 BE 규칙으로 확인한다.

**샘플 구성 (AI-11)**
- 요건 유형이 고르게 들어가게 한다.
  - 기술 (B1~B4·B10)
  - 나열·역할·운영 (B5·B8·B9)
  - 규모 (B6)
  - 도메인 (B7)
  - 태도·역량 (B12)
  - 서비스가 받지 않는 정보 (B13)
- 정답별로도 섞는다. `met`·`partial`·`unmet`이 각각 20% 이상이 되게 한다. `met`만 많으면 일치율이 부풀어 보인다.

### 채택하지 않은 안

| 안 | 채택하지 않은 이유 |
| --- | --- |
| 판정을 4단계 이상으로 나누기 (예: "인접") | 계약·화면·충족률 계산이 모두 3단계다. 경계는 `partial`과 `reason`으로 표현한다 |
| 검색 점수로 `unmet` 정하기 | 점수가 0.64~0.71에 몰려 있어 "맞는 경험 없음"을 가를 수 없다 (ADR-0001 "AI 서버 `/embed` 확인") |
| 합의가 안 되면 정답에서 빼기 | 어려운 요건이 빠지면 일치율이 부풀어 보인다. 낮은 쪽으로 넣고 표시한다 |
| 우대사항은 느슨하게 판정 | 같은 경험이 필수냐 우대냐에 따라 판정이 달라지면 사용자가 이해하기 어렵다. 구분은 충족률과 가이드 문구에만 쓴다 |

## 영향

| 담당 | 바뀌는 것 |
| --- | --- |
| AI | P3 프롬프트를 이 기준에 맞춰 고친다. 지금 `p3_v2`에 없는 규칙은 B1·B4·B5·B10·B12·B13이며, 다음 버전 `p3_v3`에 넣는다. AI-11 정답과 평가 지표도 이 기준으로 만든다 |
| BE | 없음. 연차 규칙 판정과 "낮은 쪽" 결합(D-5)은 그대로다. 운영 검수를 할 때 `llm_verdict`·`final_verdict`를 구분해 볼 수 있어야 하는데, 지금 저장 구조로 된다 |
| FE | 없음 |
| 계약 | 없음 (판정 값 3단계 그대로) |

## 위험

- **B10 때문에 결과가 높게 나올 수 있다.** 기술 목록 청크만으로 `met`을 주면, 사용자가 숙련도를 높게 적었을 때 판정도 높아진다. 사용처가 적힌 경우로만 제한했다. AI-11에서 과대 판정률이 높으면 "`skill`만 있으면 `partial`"로 바꾼다.
- **4B 모델이 경계 14개를 모두 따르기는 어렵다.** 프롬프트에는 자주 나오는 경계(B1·B2·B5·B6·B10)부터 넣는다. 나머지는 AI-11 결과를 보고 넣는다.
