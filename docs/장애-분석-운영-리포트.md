# nerdnam 장애 분석 및 운영 리포트

문서 검토일: 2026-11-04. 사례 1~5는 2026-11-03까지의 시험 기록이며, 당시 기록의 시각은 UTC(한국 시각은 +9시간)다.

## 1. 개요

운영 환경(EKS, `https://nerdnam.click`)에서 부하 시험으로 성능 저하와 장애를 일부러 재현하고, 그 과정에서 실제 장애 1건을 겪었다. 이 문서는 사례마다 **무엇이 일어났고(증상) → 왜 그랬고(원인) → 무엇을 했고(대응) → 고친 뒤 어떻게 됐는지(결과)**를 정리하고, 남은 개선 방안을 모은다.

**사례 3·4는 Redis 큐 전환 전 HTTP 경로의 실측이다.** 당시 BE 스레드 4개·HTTP 요청 마감에서 나온 수치를 현재 큐 경로의 성능으로 사용하지 않는다. 이후 ADR-0009의 큐·한도기와 BE 작업 전체 기한이 구현됐고, INFRA `06f905d`는 api·ai 큐 플래그를 켜도록 설정했다. 이 검토에서는 코드·설정을 대조했으며, 클러스터 적용과 전환 후 동일 부하 결과는 확인하지 않았다(8장).

## 2. 사례 1 — web 처리 한도 초과와 재시작

**시험:** `rate-bpjnp`, 11-03 05:03~05:09

### 증상

| 단계(초당 반복) | web 처리/초 | web p95 | 실패 | web CPU |
| --- | --- | --- | --- | --- |
| 100 | 100 | 70ms | 0 | 1.38코어 |
| 150 | **약 115에서 멈춤** | **9.2초** | 2.5%(503 약 9/초, 502 약 4/초) | **1.72코어** |

- 05:08:20 web 컨테이너가 재시작했고(exit 143), 그동안 502·503이 났다.
- 같은 시간 Grafana도 메모리 부족(OOMKilled)으로 3번 재시작했다.

### 원인

1. **web은 요청을 사실상 스레드 하나로 처리한다.** Next.js 서버는 Node.js 프로세스 1개이고, 서버 렌더링은 메인 스레드 하나가 맡는다. 요청 1건에 메인 스레드 약 8~9ms를 쓰므로 Pod 하나가 받을 수 있는 양은 **초당 약 115건**이다. CPU 1.7코어는 상한이 아니라, 메인 스레드가 꽉 찼을 때 보조 스레드(GC·압축)까지 합친 사용량이다.
2. **liveness가 "느림"을 "멈춤"으로 판단했다.** 요청이 밀려 `/healthz`도 대기열에 섰고, liveness(3초 제한 × 3회)가 실패해 kubelet이 컨테이너를 재시작했다. 과부하에서 재시작하면 처리 능력이 0이 되어 오히려 실패가 커진다.
3. **Grafana**는 부하 대시보드의 시험 변수 기본값 "All"이 라벨 없는 k6 시계열 전체와 맞아 조회가 커졌고, 메모리 상한 512Mi에 닿았다. 시험 선택이 비어 보인 것은 k6-operator가 명령줄 태그(`testrun_name`)를 붙이면 스크립트 태그(`testid`·`mode`)가 빠지기 때문이었다.

### 대응

| 항목 | 이전 | 이후 |
| --- | --- | --- |
| web 개수 | 1 고정 | **HPA 1~2개**(CPU 요청 대비 120% → 재시험 뒤 100%), metrics-server 추가 |
| web CPU 요청 | 100m | 500m(HPA 기준으로 쓰고 실제 사용량에 맞춤) |
| liveness | 20초 × 3, 3초 제한(약 1분) | **20초 × 6, 10초 제한(약 2분)**. readiness는 그대로 빨리 뺀다 |
| nerdnam quota CPU | 2코어 | 3코어(web 2개 + 롤링 업데이트 여유) |
| Grafana | 메모리 512Mi, 새로 고침 10초, 시험 "All" | 1Gi, 30초, 시험 변수를 `testrun_name`(최근 순)으로 |

app 노드가 1대(3.92코어)라 web 최대 개수는 2로 정했다. api·ai와 노드 수는 고정 그대로다.

### 결과 (재시험 `rate-dr75l`, 06:38~06:44)

- web 재시작 0, web 502·503 0. HPA가 100 단계에서 web을 2개로 늘렸다.
- 하지만 150 단계에서 **새 문제 두 가지**가 드러났다.
  - web 처리는 119/초에 그쳤고, app 노드 CPU가 0.2코어만 남았다.
  - `/api/projects`가 500을 약 3% 돌려줬다. 원인은 사례 2(Redis)다.

## 3. 사례 2 — Redis 가득 참으로 로그인 사용자 화면 500 (실제 장애)

### 경과

| 시각 | 일 |
| --- | --- |
| 11-02 ~ 11-03 05:09 | 부하 시험(smoke·rate)이 비로그인 `/api/projects`를 반복 → 세션 약 6.6만 개 누적 |
| 06:38 ~ 06:44 | rate 재시험 → 세션 약 4.4만 개 추가, **06:44 Redis 256MiB 상한 도달** |
| 06:43 ~ | BE가 세션을 쓰다가 `OOM command not allowed` → 500. 로그인한 사용자의 모든 화면이 에러 |
| 06:45 / 06:53 | Discord 알림 `NerdnamRedisRejectingWrites`(쓰기 거절) / `NerdnamRedisMemoryHigh`(메모리 80%, 10분 지속) |
| (발견) | 팀원이 `https://nerdnam.click/` 에러를 보고 |
| 복구 | 로그인 정보가 없는 세션 110,660개 삭제(로그인 세션 3개 유지) → Redis 256MiB → 1.87MiB, 화면 정상 |

### 원인

1. Spring Security는 로그인하지 않은 요청이 보호된 경로(`/api/**`)에 오면 401을 주면서, 로그인 뒤 돌아가려고 **원래 요청을 세션에 저장**한다(RequestCache). 기본 동작이다.
2. 세션 수명이 7일이라, **비로그인 API 요청 1번 = Redis에 7일짜리 세션 1개**가 됐다.
3. Redis는 `noeviction`이라 가득 차면 모든 쓰기를 거절한다. 로그인 사용자도 요청마다 세션 접근 시각을 쓰므로 **로그인 기능 전체가 500**이 됐고, 세션이 7일 남아 **저절로 풀리지 않는다.**
4. web(서버 렌더링)도 쿠키가 없는 방문에서 BE를 불러 같은 세션을 만들었다.

부하 시험에서 드러났지만 부하 시험만의 문제는 아니다. 누구든 비로그인으로 API를 반복해 부르면 같은 장애를 만들 수 있다.

### 원인 찾기에서 배운 것

- 처음에는 `kubectl logs`가 비어 있어 원인을 놓칠 뻔했다. **Loki**에서 BE 오류 로그(`RedisSystemException … OOM`)를 찾아 원인을 확인했다.
- 알림은 장애 1~2분 만에 Discord로 갔지만, 조치는 팀원 보고 뒤에 했다. 알림 채널을 보는 습관이 필요하다.

### 대응과 재발 방지

| 항목 | 내용 |
| --- | --- |
| 즉시 복구 | Redis에서 `SPRING_SECURITY_CONTEXT`가 없는 세션만 골라 삭제(Lua로 확인 후 UNLINK) |
| BE #63 | 로그인 안 된 요청이 Redis에 빈 세션을 만들지 않게(`/api/**` 401 때 요청을 저장하지 않음) |
| BE #65 | 로그인 전 세션은 10분, 로그인하면 7일 |
| FE `3da158b` | 쿠키 없는 방문은 BE를 부르지 않음(로그인 안 한 방문마다 빈 세션이 쌓이지 않게) |
| 부하 시험 | BE 수정이 배포될 때까지 중지 |

### 결과

- 배포 후 비로그인 `/api/projects` 5번 호출에 새 세션 0개. 로그인 시작(OAuth) 1번에 세션 1개(10분 이하).
- 이후 rate·concurrency 재시험(사례 5)에서 `/api/projects` 500 0건.

## 4. 사례 3 — AI 작성 방향 몰림 (Nova 한도)

**시험:** `ai-guide-9pfpg`, 08:54~09:09. 이미지 BE `7eb24db`·AI `7f5f828`. 근거: [ADR-0008](../adr/0008-bedrock-throttle-handling.md) 시나리오 B(예상: 저하형).

### 증상

| | 정상(분당 3건 × 탭 5개) | 몰림(분당 6건 × 탭 5개) |
| --- | --- | --- |
| 작업 | 완료 75 | 완료 128, 실패 5(`gpu_unavailable` 3, `ai_error` 2), 건너뜀 22(같은 공고 진행 중 409) |
| 완료 시간 p50 / p95 | 약 7초 / 10~17초 | 끝 무렵 **166초 / 192초** |
| BE AI 작업 큐 | 0~1 | 최대 **39** |
| BE 작업 스레드 | 4개 중 3~4 | 4개 모두 사용 |
| Nova 호출(`converse`) | 분당 12~20회, 재시도 없음 | 분당 20~30회 + throttle, 시도 ÷ 호출 **약 2배** |
| AI 서버 대기열 | 대기 0 | 대기 0, 거절 0 |

### 원인

1. 작성 방향 탭 1개 = Nova 호출 1번이다. 몰림(분당 30탭)이 **Nova 계정 한도(분당 약 20번)**를 넘어 throttle이 났다.
2. AI 서버는 throttle을 실패로 돌려주지 않고 요청 마감 안에서 쉬었다가 다시 보낸다. 그래서 호출 하나가 길어진다.
3. 호출이 길어지니 **BE AI 작업 스레드 4개**가 오래 붙잡혀, 뒤 작업이 BE 큐에 쌓였다. AI 서버 대기열은 비어 있었으므로 병목은 BE 앞단과 Bedrock 한도다.
4. 실패 5건은 몰림 끝 무렵, 재시도해도 한도가 풀리지 않거나 AI 오류가 난 경우다.

### 결과 판단

예상한 "저하형"이 재현됐다(ADR-0008 판정 기준: 큐 10 이상 지속 = 저하). 정상 단계로 돌아가면 큐가 풀리고 실패는 소수다.

## 5. 사례 4 — AI 공고 분석 몰림 (Titan 한도)

**시험:** `ai-analysis-vrmgt`, 09:11~09:30. 근거: ADR-0008 시나리오 A(예상: **장애형**, 분당 5건이면 실패 약 64%).

### 증상

| | 정상(분당 2건) | 몰림(분당 5건) |
| --- | --- | --- |
| 작업 | 완료 10 | 완료 25, **실패 0** |
| 완료 시간 p50 / p95 | 약 19초 / 20~50초 | 끝 무렵 **169초 / 207초** |
| Titan 호출(`invoke_model`) | 분당 40회 | **분당 60회에서 더 늘지 않음**, 시도 ÷ 호출 1.5~3.7배 |
| AI 서버 임베딩 대기 p95 | 0.4초 | 10초 이상 |
| AI `/embed` 응답 p95 | 0.5초 | 약 115초(35건 중 8건이 60~120초 구간. 히스토그램 추정치로 개별 요청의 110초 이내 종료를 단정할 수 없음) |
| BE 큐 / 스레드 | 0 / 1~2 | 최대 6 / 4개 모두 사용 |

### 원인

1. 분석 1건 = 요건 임베딩 20번이다. Titan 계정 한도가 분당 약 60번이라, **처리할 수 있는 양은 분당 약 3건**이다. 분당 5건이 들어오면 임베딩이 밀린다.
2. 예상과 달리 실패가 없었던 이유는 두 가지다.
   - AI 서버가 throttle을 받으면 바로 실패하지 않고, 마감(110초) 안에서 기다렸다 다시 보낸다(AI #46). 최종 분석 실패는 0건이었다. 응답 시간 구간만으로 개별 `/embed`의 마감 초과·재시도 여부까지 확인한 것은 아니다.
   - **BE 작업 스레드 4개가 동시에 도는 분석을 4건으로 묶었다.** Titan에 한꺼번에 몰리는 양이 제한되어, 한도를 넘는 정도가 시뮬레이션보다 작았다.
3. 결과적으로 한도 초과는 실패가 아니라 **지연(19초 → 약 3분)**으로 나타났다.

### 결과 판단

이 이미지 기준으로 시나리오 A는 **"저하형, 분당 약 3건에서 포화"**다. 다만 당시 HTTP 경로에서는 `/embed`가 마감 110초에 가까워졌으므로, 몰림이 더 길거나 세면 마감 초과(503) → 분석 실패로 바뀔 수 있었다. 이번 시험은 그 직전에서 끝났다. 이 결과는 ADR-0009의 배경에 반영됐으며, 큐 경로는 HTTP 요청 마감 대신 BE 작업 전체 기한을 기준으로 다시 측정해야 한다.

| 150 단계 web 처리 | 약 115/초 | 119/초 | **150/초** |
| 150 단계 web p95 | 9.2초 | 3.46초 | 수십 ms |
| 실패 | 2.5%(web 502·503) | 3%(`/api/projects` 500) | **0** |
| web 재시작 | 1회 | 0 | 0 |

### 남은 한계

- 사용자를 200 → 300명으로 늘려도 처리량은 129 → 151로만 늘고 응답 시간이 두 배가 됐다. **처리량은 초당 약 150회에서 포화**한다.
- 병목은 **web Pod 하나당 약 1코어**(메인 스레드 한도)다. Pod 2개가 모두 여기에 닿았다. 노드에는 1.2코어가 남지만 HPA 최대가 2라 더 늘지 않는다.

## 7. 운영 중 드러난 문제

시험과 대응 과정에서 장애는 아니지만 운영 절차의 빈틈이 드러났다.

| 문제 | 영향 | 처리 |
| --- | --- | --- |
| Alertmanager 설정을 바꾸고 `kube-prometheus-stack`만 sync | 설정값은 `nerdnam-root`가 넘겨주므로 반영되지 않았는데, 화면은 Synced로 보임 | root부터 sync하도록 INFRA 문서에 순서 추가 |
| 열린 이슈의 "배포 보류" 요청을 확인하지 않고 AI 배포 PR merge | ADR-0008 "전·후" 비교의 "전" 측정 불가 | 팀이 최신 이미지로 한 번만 측정하기로 결정(SPEC #96). 배포 PR merge 전에 보류 요청을 확인 |
| 부하 시험 2개가 동시에 실행됨 | 서로 결과를 오염 | load-test quota를 시험 하나 크기(800m)로 줄임 |
| k6 AI 완료 시간이 1000배 작게 기록(밀리초 대신 초를 넣음) | 대시보드 "작업 완료 시간"이 0.01~0.2초로 보임 | INFRA #30에서 수정. 사례 3·4의 시간은 1000을 곱해 보정한 값 |
| `load-test.sh`가 AI 시험의 예상 시간을 0분으로 계산 | 제한 시간이 15분뿐이라 885초 걸린 시험이 거의 강제로 멈출 뻔함 | INFRA #30에서 수정 |
| AI 시험 계정이 실제 팀원 계정(회원 1) | 분석이 그 계정의 실제 프로젝트도 근거로 읽음. 탈퇴로 정리할 수 없음 | 시험 공고(3~12)만 쓰고 실제 공고 제외, 시험 뒤 로그아웃 |

## 8. 개선 방안

### AI 큐 전환 반영 현황 (2026-11-04 코드·설정 기준)

| 항목 | 반영된 내용 | 운영에서 확인할 것 |
| --- | --- | --- |
| BE 큐 경로(BE #68) | Redis Streams에 단계별 요청, Pod별 `reply_to` 결과 대기. 가상 스레드 64·내부 대기 200 | BE 내부 큐가 작아도 Redis lag·pending과 한도기에서 대기하는지 확인 |
| 작업 기한·접수 보호(BE #68·#69·#70) | 접수부터 `job-timeout=20m`, 호출별 `wait-timeout=20m`, 같은 id로 5분마다 재전송. 사용자 요청 `XLEN(llm)+XLEN(embed)` ≥ 200·큐 연결 불가 등은 작업 생성 전 503 `AI_UNAVAILABLE` | 시작 요청 거절과 접수 후 `TIMEOUT`·`GPU_UNAVAILABLE`·`AI_ERROR`를 별도 집계. 생존 기록 기준 정리 `stale-after=25m`와 작업 기한을 구분 |
| AI 작업자·한도기(AI #54·#55) | 스트림별 작업자 8·2·1, 사용자 임베딩 우선. Bedrock 호출마다 Nova 20·Titan 60회/분 한도기 적용, HTTP·큐 공용 | 한도기는 프로세스 메모리이며 현재 TPM은 제한하지 않음. throttle이 없어도 `limiter` 대기 증가를 확인 |
| 세션·큐 Redis 분리(INFRA #32) | 큐 Redis 256MiB·noeviction, AOF·RDB·PVC 없음. 요청·결과 삭제와 TTL, exporter·ACL·NetworkPolicy·큐 알림 3개 추가 | 큐 Redis 재시작 유실·재전송·중복 억제, 메모리와 메시지 정리 확인. BE 재시작 후 작업 자동 재개는 미지원 |
| 큐 경로 켜기(INFRA #47) | `gitops/apps/values.yaml`에서 api·ai `AI_QUEUE_ENABLED=true`. 이미지 설정 BE `22b53f6`·AI `a0b1c60` | 실제 sync·Pod 환경 확인 후 같은 부하 재시험. 이 리포트에는 전환 후 성공 결과가 아직 없음 |

큐 전환의 성공 기준은 처리 시간 단축보다 **불필요한 재시도 감소와 기한 내 완료**다. 모델 한도가 처리량 상한인 점은 그대로이고, 무한히 몰려도 실패하지 않는다고 보장하지 않는다. 같은 부하에서 Bedrock 시도/호출 비율 ≈ 1, 작업 실패 0, 몰림 종료 후 대기 감소를 확인한다.

### 우선순위 높음

| 방안 | 이유 | 담당 |
| --- | --- | --- |
| Redis 메모리 알림을 **조치로 연결**: 알림 채널 담당자 지정, `NerdnamRedisRejectingWrites`에 대응 절차(로그인 없는 세션 정리) 링크 | 사례 2에서 알림은 1~2분 만에 갔지만 조치는 사용자 보고 뒤였다 | INFRA |
| 큐 전환 후 `ai-guide`·`ai-analysis`를 사례 3·4와 같은 부하로 재시험 | 전환 전 실측만 있다. 재시도 비율·실패·완료 시간·스트림별 lag·pending·단계별 대기를 비교 | INFRA·AI·BE |
| 같은 부하 확인 뒤 몰림을 더 길게(`DURATION_SURGE=15m`) 또는 세게(`RATE_SURGE=8`) 시험 | 작업 기한 20분·접수 상한 200·메모리 보호가 언제 작동하는지 확인(Bedrock 요금 추가) | INFRA·AI |
| 큐 재시험의 `JOB_TIMEOUT_SECONDS=1500` 설정, 실패 종류 분리 | 기본 k6 대기 600초는 BE보다 먼저 포기한다. `timeout_k6`·접수 `http_503`·작업 `timeout`을 섞으면 큐 성능을 오판 | INFRA |
| `NerdnamAiJobQueueBacklog` 안내 문구의 `stale-after 20분` 수정 | 실제 BE는 작업 기한 20분, 마지막 생존 기록 기준 정리 25분. lag·pending 알림은 30분(문서 60분)이므로 작업 실패도 함께 감시 | INFRA |

### 처리량을 더 받아야 할 때

| 방안 | 효과 | 비용·영향 |
| --- | --- | --- |
| FE 첫 화면(`/`) 캐시 | 요청 하나에 드는 CPU 자체가 줄어 효과가 가장 크다 | FE 작업 |
