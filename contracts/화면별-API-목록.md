# 화면별 API 목록 (C-02 초안)

> 상태: **FE 초안** · 기준: `기획서.md` v1.19, `adr/0002-project-registration-rules.md`, `design/`
> 다음 단계: BE가 엔드포인트(메서드·경로)를 붙이고, "확인할 것"을 함께 정한 뒤 → `web-api.openapi.yaml`(C-03)로 옮긴다.

이 문서는 화면마다 **서버와 주고받아야 하는 데이터**를 정리한 목록입니다. FE가 "화면에 무엇이 필요한가"를 적고, BE가 "어떤 API로 줄 것인가"를 채웁니다. 엔드포인트 칸이 비어 있는 것은 BE가 정할 부분입니다.

## 읽는 법

| 칸 | 뜻 |
| --- | --- |
| 언제 | 화면이 열릴 때 / 사용자가 무언가를 눌렀을 때 / 입력할 때마다 |
| 필요한 데이터 | 주고받는 값. 필드 이름은 기획서 4장 기준, 없으면 한글로 적음 |
| 엔드포인트 | BE가 채움 |

- **조회**: 서버에서 받아 화면에 보여 주는 것
- **저장·변경**: 사용자 동작을 서버에 보내는 것
- **확인할 것**: 기획서·디자인만으로는 정해지지 않아 BE(또는 팀)와 정해야 하는 것
- 화면 안에서만 바뀌는 것(탭 전환, 필터, 펼치기, 복사)과 누구에게나 같은 고정 문구(숙련도 기준, 작성 가이드, 고용형태 선택지)는 API가 필요 없어 적지 않았다.

## 공통 (모든 화면)

재료: 기획서 5장·8장, 작업목록 BE-03·D-7

### 조회

| 언제 | 필요한 데이터 | 엔드포인트 |
| --- | --- | --- |
| 로그인 후 화면이 열릴 때 | 내 정보: 사용자 id, 이름(머리글 동그라미에 첫 글자 표시), 이메일 | |
| 로그인 후 화면이 열릴 때 | 온보딩 진행 상태: 어느 단계까지 했는지 (기술스택·경력·프로젝트 입력 여부, 확정 프로젝트 수), **검토 중인 프로젝트 id**(있으면 S02·S03에 "검토로 돌아가기", S04 들어갈 때 경고). 로그인 직후 어느 화면으로 보낼지 정하는 데도 씀 | |
| AI 작업을 요청한 뒤 몇 초마다 (폴링) | AI 작업 상태: 작업 id → 상태(진행 중·완료·실패), 실패 이유(GPU 서버 꺼짐 / 그 밖의 오류), 완료되면 결과를 다시 조회할 대상 id | |

### 저장·변경

| 언제 | 필요한 데이터 | 엔드포인트 |
| --- | --- | --- |
| 머리글 계정 메뉴 → 로그아웃 | - | |
| 머리글 계정 메뉴 → 탈퇴 | - (탈퇴 시 원본·벡터 즉시 삭제, 기획서 8장) | |

### 확인할 것

1. **인증 방식**: 쿠키 세션인지 토큰(헤더)인지. 웹의 API 호출 코드와 Next.js 서버 쪽 호출 방식이 달라진다. 기획서 5장 Redis에 "세션"이 있어 쿠키 세션으로 짐작됨.
2. **오류 응답 공통 형식**: 모든 API가 같은 모양으로 오류를 돌려줄지 (예: 오류 코드, 사용자에게 보여 줄 메시지, 입력 칸별 오류). S07처럼 칸마다 오류를 보여 주는 화면이 있다.
3. **오래 걸리는 AI 작업 (v1.11 제안)**: 재구성(15초)·적합도 분석(20초)·작성 방향(60초) 모두 **웹↔API는 작업 상태 조회(폴링)**로 받는다. 요청하면 작업 id를 받고, 위 "AI 작업 상태"를 몇 초마다 다시 묻는다. 새로고침하거나 화면을 나갔다 와도 이어서 기다릴 수 있다. API↔AI 사이 방식은 BE·AI가 정한다. 함께 정할 것:
   - **폴링 간격과 작업 id 방식**: 몇 초마다 물을지, 작업 id를 따로 둘지 프로젝트·공고 id로 대신할지.
   - **GPU 서버가 꺼져 있을 때** (기획서 8장, ADR-0001): 실패 이유로 다른 오류와 구분해 주면 웹이 "잠시 후 다시 시도해 주세요"를 띄운다.
   - **같은 프로젝트의 AI 요청은 동시 1건** (ADR-0002): 이미 진행 중일 때 두 번째 요청에 어떤 응답이 오는지. 화면 조회 응답에 "진행 중인 작업 id"가 있으면 웹이 버튼을 막고 로딩을 이어서 보여 줄 수 있다.
4. **계정 메뉴**: 디자인에 동그라미 버튼만 있고 메뉴 내용(로그아웃·탈퇴·설정)이 없다.

## S01 시작하기

재료: `design/index.html`, 기획서 6장, 작업목록 FE-04·BE-03, D-8

### 조회

| 언제 | 필요한 데이터 | 엔드포인트 |
| --- | --- | --- |
| 화면이 열릴 때 | 이미 로그인한 사용자인지 (공통의 "내 정보"를 재사용). 로그인 상태면 다음 화면으로 보냄 | |

### 저장·변경

| 언제 | 필요한 데이터 | 엔드포인트 |
| --- | --- | --- |
| "Google 계정으로 계속" | 소셜 로그인 시작 → 로그인 후 돌아올 주소 | |
| "카카오 계정으로 계속" | 소셜 로그인 시작 → 로그인 후 돌아올 주소 | |
| "이메일로 시작하기" | `email`, 개인정보 동의 여부 | |
| 로그인(가입) 완료 시 | 개인정보 동의 기록: 동의 여부, 동의한 약관 버전, 동의 시각 (BE-03 "동의 기록") | |

### 확인할 것

1. **이메일 로그인 방식**: 디자인에는 이메일 칸만 있고 비밀번호 칸이 없다. 이메일로 로그인 링크를 보내는 방식(매직 링크)인지, 비밀번호를 받는지.
2. **소셜 로그인 제공자**: Google·카카오 둘 다인지 (D-8).
3. **로그인 후 이동할 화면**: 처음 가입 → S02, 온보딩 중이던 사용자 → 하던 단계, 온보딩 끝난 사용자 → S06. 이 판단에 공통의 "온보딩 진행 상태"가 필요.
4. **개인정보 처리방침·이용약관 화면**: 링크만 있고 내용·화면이 없다.

## S02 기술스택 입력

재료: `design/skills.html`, `design/assets/js/skills.js`, 기획서 F1·4.1, 작업목록 FE-05·BE-04·BE-06

### 조회

| 언제 | 필요한 데이터 | 엔드포인트 |
| --- | --- | --- |
| 화면이 열릴 때 | 내가 추가한 기술 목록: 기술 id, `name`(표준 이름), `category`, `level`(1~4) | |
| 화면이 열릴 때, 카테고리 탭을 바꿀 때 | 카테고리별 "자주 쓰는 기술" 추천 목록: `name` 여러 개 | |
| 검색창에 입력할 때마다 | 기술명 자동완성 후보 (표준 사전): `name`, `category`. 예: "k8s" → Kubernetes | |

### 저장·변경

| 언제 | 필요한 데이터 | 엔드포인트 |
| --- | --- | --- |
| 추천 칩·검색 결과로 기술 추가 | `name`(표준 이름), `category`, `level`(처음엔 1 · 학습 중) | |
| 숙련도 막대를 누를 때 | 기술 id, 바꾼 `level` | |
| 삭제(✕)를 누를 때 | 기술 id. 경력·프로젝트에서 쓰는 기술이면 삭제를 거부하고 **어디서 쓰는지**(예: "OO커머스 경력에서 사용 중")를 돌려준다 (ADR-0002 Q7) | |

### 확인할 것

1. **저장 시점**: 추가·숙련도 변경·삭제를 **누를 때마다 바로** 서버에 보낼지, **"다음" 버튼에서 한 번에** 보낼지. 디자인에는 별도 저장 버튼이 없고, 기획서 F3는 "기술스택은 저장 즉시 RAG 등록"이라 매번 보내면 임베딩도 매번 일어남.
2. **추천 목록 출처**: "자주 쓰는 기술"을 서버가 줄지, 웹에 고정 목록으로 둘지. 디자인은 카테고리마다 4개 고정.
3. **사전에 없는 기술**: 검색해도 표준 사전에 없을 때 S02에서 직접 추가할 수 있는지. S04에서는 "없는 기술은 바로 추가"가 가능함(F1). S02 디자인에는 이 경우가 없음.
4. **카테고리 값**: 화면 표시(언어·프레임워크·DB·인프라·협업 도구)와 저장 값(`language`, `framework`, `database`, `infra`, `tool`, 기획서 4.1)의 대응을 계약에 그대로 쓸지.
5. **삭제 거부 응답 모양**: 사용처 목록을 어떤 형태로 줄지 (사용처 종류·이름). 삭제 전에 미리 알 수 있게 목록 조회에 "사용 중" 표시를 같이 줄지.

## S03 경력 입력

재료: `design/career.html`, `design/assets/js/career.js`, 기획서 F1·4.2, 작업목록 FE-06·BE-06

### 조회

| 언제 | 필요한 데이터 | 엔드포인트 |
| --- | --- | --- |
| 화면이 열릴 때 | 내 경력 목록 (최신순): 경력 id, `company`, `team`, `job_title`, `position`, `employment_type`, `start`, `end`(재직 중이면 없음), `duties[]`(최대 5줄), `skills[]`(기술 id) | |
| 화면이 열릴 때 | "이 회사에서 쓴 기술" 선택지 = 내 기술스택 목록 (S02의 조회를 재사용) | |

### 저장·변경

| 언제 | 필요한 데이터 | 엔드포인트 |
| --- | --- | --- |
| "경력 추가" 후 "저장" | 위 경력 필드 전체 (새 경력) | |
| 기존 경력 수정 후 "저장" | 경력 id + 위 경력 필드 전체 | |
| "삭제" | 경력 id. 프로젝트가 연결된 경력이면 삭제를 거부하고 **연결된 프로젝트 목록**을 돌려준다. 웹은 "프로젝트 소속을 개인으로 바꿔 주세요"라고 안내한다 (ADR-0002 Q8) | |

### 확인할 것

1. **저장 시점**: S03에는 "저장" 버튼이 있는데, FE-09는 "단계 이동 시 자동 저장"이다. 저장을 누르지 않고 다른 경력 카드나 "다음"을 누르면 자동 저장할지, 버리고 경고할지.
2. **필수 항목**: 기획서 4.2는 `team / job_title`을 한 줄로 묶어 필수로 적었는데, 디자인은 "부서"·"직무" 두 칸이다. 둘 다 필수인지.
3. **"경력이 없어요 (건너뛰기)"**: 건너뛴 사실을 서버에 남길지 (온보딩 진행 상태 판단에 필요할 수 있음).
4. **재임베딩 안내**: 확정 사례에 연결된 경력을 고치면 해당 청크만 다시 임베딩한다(F1). 웹이 사용자에게 따로 알릴 것이 있는지, 아니면 서버 내부 처리로 끝나는지.
5. **소속 바꾸기 안내의 이동 위치**: 경력 삭제가 거부됐을 때 연결된 프로젝트로 바로 가는 링크를 줄지. 그 프로젝트가 확정 상태면 소속을 바꾸는 것도 재등록(ADR-0002 Q6)이 필요한지.

## S04 프로젝트 입력

재료: `design/project.html`, `design/assets/js/project.js`, 기획서 F1·4.3, 작업목록 FE-07·BE-07
주소: 새 프로젝트 `/projects/new`, 저장된 프로젝트 `/projects/[projectId]` (번호 없는 `/projects`는 S06으로, 기획서 v1.11)

### 조회

| 언제 | 필요한 데이터 | 엔드포인트 |
| --- | --- | --- |
| 화면이 열릴 때 | 내 프로젝트 목록 (위쪽 탭): 프로젝트 id, `title`, `status`(초안·검토 중·확정 → 탭의 "작성 중"/"확정" 배지) | |
| 탭을 고를 때 | 프로젝트 상세: `title`, `period`(start·end), `career_id` 또는 개인·팀 프로젝트 구분, `skills[]`, `raw_text`(본문), GitHub 링크, 배포·문서 링크. 재등록 중이면 이전 확인 질문 답변도 채워져 온다 (ADR-0002 재등록 1) | |
| 화면이 열릴 때 | "소속" 선택지 = 내 경력 목록 (S03의 조회를 재사용). 개인·팀 프로젝트는 고정 선택지 | |
| 화면이 열릴 때 | "사용 기술" 선택지 = 내 기술스택 목록 (S02의 조회를 재사용) | |

### 저장·변경

| 언제 | 필요한 데이터 | 엔드포인트 |
| --- | --- | --- |
| 탭의 "추가" | 새 프로젝트 만들기 (빈 초안) | |
| 화면에 들어올 때 (검토 중인 결과가 있으면, 경고 후) | 프로젝트 id → 확정 전 검토 결과 버리기 (기획서 v1.14 검토 결과 유지 규칙) | |
| 단계를 옮길 때 (자동 저장) | 프로젝트 id + 위 상세 필드 | |
| "기술스택에 없는 기술 추가" | 기술 이름 → 기술스택에 "학습 중"으로 생성 + 이 프로젝트에 연결 (BE-06) | |
| "[문제]-[해결]-[결과]로 재구성하기" | 프로젝트 id → 재구성 시작 (AI `/restructure`, 15초 목표, 작업 상태 조회로 완료 확인) → S05로 이동 | |

### 확인할 것

1. **자동 임시 저장 시점**: 입력을 멈추고 몇 초 뒤 / 탭을 바꿀 때 / 화면을 떠날 때 중 언제 보낼지.
2. **재구성 중 화면 (FE·디자인)**: 기다리는 방식은 공통 3번(폴링). 로딩을 S04에서 보여 줄지 S05로 먼저 이동해 보여 줄지, 디자인이 없다.
3. **개인·팀 프로젝트 구분 값**: 기획서 4.3에는 `career_id`만 있다. 경력이 없는 "개인 프로젝트", "팀 프로젝트(회사 외)"를 어떤 값으로 저장할지.
4. **링크 필드**: 기획서 F1에는 있지만 4.3 데이터 구조에는 없다. (이미지는 ADR-0004로 제거 — S04에서 받지 않는다.)
5. **새로 추가한 기술의 정규화**: 사전에 없는 이름(예: Spring Cloud Gateway)을 그대로 저장하는지, 사전에 있으면 표준 이름으로 바꿔 주는지. 바뀌면 웹이 바뀐 이름을 받아야 한다.
6. **검토 결과 버리기를 따로 부를지**: S04에 들어올 때 웹이 "버리기"를 요청할지, 서버가 "재구성하기" 요청을 받을 때 이전 검토 결과를 알아서 버릴지. 후자면 S05에서 온보딩 밖으로 나갈 때만 따로 부르면 된다.
7. **프로젝트 삭제**: 디자인에 삭제 버튼이 없다. 필요한지.

### 저장·변경

### 확인할 것

1. **"이 버전으로 바꾸기"의 저장 방식**: 고른 버전 내용을 복사해 새 최신 버전(v3)을 만드는지, 고른 버전(v1)을 다시 "현재 버전"으로 가리키는지. 디자인 예시는 v3로 복사하는 방식으로 만들어 두었다 (버전 기록이 한 방향으로만 쌓임).
2. **이전 버전의 확인 필요**: v2가 v1의 확인 질문에 답해 만든 버전이면, v1으로 바꿀 때 v1의 확인 필요가 다시 살아나는지.
3. **"답변 추가" 동작**: 답을 보낼 때마다 바로 새 버전을 만드는지(AI 호출), 한 사례의 질문에 모두 답한 뒤 한 번에 만드는지. 디자인은 답변 추가 즉시 질문이 사라진다.
4. **"직접 편집"이 새 버전인지**: 직접 고친 내용을 v3처럼 새 버전으로 남기는지, 현재 버전을 덮어쓰는지. 직접 편집한 내용에 원문에 없는 수치가 들어가면 `unverified`로 다시 잡는지.
5. **AI 작업 대기**: 공통 3번(폴링). 수정 요청·다시 나누기·답변 추가가 모두 AI 호출이고, 같은 프로젝트는 동시에 1건만 된다.
6. **`source_spans` 기준 텍스트**: 문자 위치가 원래 원문 기준인지, 답변을 덧붙인 원문 기준인지.
7. **사례 결정 저장 시점**: 확정·제외를 누를 때마다 바로 저장해야 화면을 떠났다 돌아와도 유지된다(F1). 매번 저장으로 가정함.
8. **떠날 때 경고와 버리기 (기획서 v1.14)**: 확정 전에 S04나 온보딩 밖으로 나가면 웹이 경고 후 "검토 결과 버리기"를 요청한다(S04 확인할 것 6번). 브라우저 창을 그냥 닫으면 경고·요청을 보낼 수 없으므로, 그 경우는 다음에 S04에 들어갈 때 버린다.
9. ~~**확정·제외한 사례의 편집**~~ → **결정 (기획서 v1.19):** 확정·제외한 사례는 내용을 바꿀 수 없다. 카드를 펼쳐도 읽기 전용으로 보여 주고, 수정 요청·직접 편집·이 버전으로 바꾸기·확인 질문 답변·빼고 진행 버튼은 숨기거나 막는다. 고치려면 "다시 검토하기"를 먼저 누른다(누르면 카드가 펼쳐져 바로 고칠 수 있다). 확정 ↔ 제외는 바로 바꿀 수 있다. 서버도 같은 규칙으로 거부한다(422 `DOMAIN_RULE_VIOLATED`). **FE 할 일:** 지금 디자인(`design/assets/js/review.js`의 `bodyHtml`)은 상태와 관계없이 같은 버튼을 그리므로 FE-08 구현 때 상태별로 나눈다.

### 확인할 것

1. **생성 시점**: 다섯 탭을 리포트 직후 한꺼번에 만드는지, 탭을 열 때 그 탭만 만드는지. 다시 들어왔을 때 저장된 결과를 바로 주는지(BE-14 Redis 캐시).
2. **탭별 상태 (v1.11 제안)**: 웹은 SSE 대신 탭마다 "생성 중·완료·실패"를 조회한다(공통 3번). 다섯 탭의 상태를 한 번에 줄지 탭마다 따로 줄지, 생성 중에 이미 완성된 부분(문단 일부)도 줄지.
3. **경력기술서 미리보기의 데이터**: 디자인의 "미리보기"를 바꿔 쓰기 표로 웹이 만드는지, 서버가 따로 주는지.
4. **다시 만들기 제한**: 횟수 상한이 있는지. S05의 재구성은 상한을 없앴는데(ADR-0002 Q1), 작성 방향(60초, 비용이 더 큼)도 같은 원칙인지.
5. **근거 링크 이동 위치**: S08 확인할 것 2번과 같음.
